--------------NEXTJS--------------------

-- NextJS is a full stack framework. both are deployed in a single instance.. Both front end and backend can be served from the same instance. 
-- We can have single codebase for both. No Cors issues. 


Reasons to use NextJS Over reactjs--
1. Waterfalling - 
		initial rendering is slow as whenever we hit a particular link, first the CDN sends HTML Page..
		and then the JS file mentioned in script tag is sent by server.. then we do authentication and based on that client renders.. this condition is kinda waterfalling. 
		we have lot of round trips that are happening sequentially. 
		NOTE: IN REACTJS - WE MAKE BUILDS OF THE JSX FILE AND ITS WRAPPED INTO HTML FILE WHICH HAS JS FILE IN ITS SCRIPTS.. WHICH DOES OUR REACT CODE. 
	NOTE: WHAT IF IN A SINGLE REQUEST, WE GET A INITIAL RENDERED PAGE. this is provided by nextjs. 
2. No JS - sometimes when we want to send email as an HTML page, we are not allowed to use JS in there.. as mail providers block JS execution for security reasons. 
3. Not SEO optimized initially - Search engines scraps website through HTML page only and not js. 
				GOOGLE LISTS WEBSITE BASED ON THE INFO THAT IT GETS FROM HTML AND NOT JS.  initially this used to happen but now web crawlers of google have become much more advanced. if ours is a course selling website, if initial html doesn't have courses , then it wont be be able to recoginize if its a course selling website. 
				IT RANKS IT ON GOOGLE BASED ON THE HTML IT GETS BAC. CRAWLERS DONT RUN OUR JS FILE TO RENDER OUR PAGE TO SEE FINAL OUTPUT. 
4. Seperate front/backend code - We have to create seperate frontend and backend.
5. No react-router-dom inclusion - React doesn't provide react router-dom by default.. we have to add it. 

-------------------for SEO-----------------
WE CAN ALSO PUT TEXT IN META TAG. but everytime we will have to put meta tag, as our application grows. f

Solution to all of this: 
----------Server side rendering - SSR - 
1. to avoid waterfalling - in SSR, the html page is first rendered on the server side and then is sent as a field HTML page to the client. 
2. low bundle size - also it can load libraries on the server side itself to reduce bundle size which is not required to be sent to the client. 
3. Direct access to backend - as backend is closer to the server it can directly query backend services to get the data hence minimizing latency issues. 
4. No need of express - as we can directly write http backend routes in nextjs app.  

Disadvantages of SSR -
1. Subsequent rendering happens on the client side only initial rendering happens on the server side. 
2. SSR doesn't understand state variables and hooks as its rendered on the server side.. it just takes the initial value set during useState declaration and wraps it into html page and then sends it to the client. 
3. SSR doesn't have access to browser objects, window objects and localStorage as this is only available on the browser side. 
4. cannot do lazy loading in ssr. 

FOR THE INITIAL RENDER IN SSR, IF WE HAVE DATA COMING FROM API, THERE WILL BE A SLIGHT DELAY UNTIL THE DATA COMES FROM SERVER.
TO REDUCE THIS, We can implement "getServerSideProps" function with export default and return the data as props in the same file which is going to be rendered on initial load. 

	export default function getServerSideProps (){
	
	const data = doAPICalling()
	return {props : {data } }
	}
	and the component can get the data in its props. now the data is fetched on server side and is rendered

----------------CSR VS SSR VS SSG (static site generation)----------------------------
-- CSR - client side rendering - rendering of a webpage is done on browser using Javascript. instead of server sending a full fledged rendered HTML page to client. 
		
 - FLOW IN CSR - we call request for page. it gives an empty html page with some script tag. and then request is sent for that js script (chunk.js) and it gives us JS code and our actual rendering components. JS on browsers runs all the code in js script returned from server to render the page.
 - PRODUCTION DEPLOYMENT - we run npm run build which generates a dist folder and the dist folder is uploaded to s3 bucket and CDN is connected to it. 
 
 - DISADVANTAGE - it takes few millisecond to render the page.. there's some time between requesting for index.html and network request call to get the js script and then it executes the js script to render the page. 
 - NO SEO optimized - - as web crawlers like google only scans first rendered HTML file to rank it on search engine. 
 - User sees a flash before rendering 
 - Waterfalling problem - lot of network calls just for initial render. 

-- SSR - When rendering process (process of converting JS components to HTML page) happens on the server, its called as SSR. 
  - Flow in SSR - in the first request only, it requests the server and server gets all the data from DB based on the user and gives back fully rendered page on first network request. 
  - Advantage -  SEO optimized as we get all data in first render. no waterfalling problem. no white flash before initial render. 
  
 - DISADVANTAGES OF SSR -
	- Expensive on the server side since every request needs to render on the server. So server does a lot of computing to this rendering on its end to send the client html. 
	- Harder to scale, as we can't cache it on CDNs.

----------------------------SINGLETON PRISMA CLIENT----------------------------------------------
When instantiating prisma client in Nextjs in dev mode - we might come across an error - There are already 10 instnaces of prisma client running actively.
Because the thing is, each time next run dev is run, it clears nodejs cache on hot reload. so it has to initialize a new PrismaClient client everytime we make any change and save which can exhaust the database connections as each PRISMACLIENT INSTANCE HOLDS ITS CONNECTION POOL. 

Best practice is to use Singleton client for managing prisma connection client.  sAVE THE PRISMA CLIENT INSTANCE TO GLOBALTHIS Object. and check if it exists on GlobalThis object and only instantiate a new prisma client connection its not existing in GlobalThis Object. 

import { prismaClient } from @prisma/client;

const prismaClientSingleton = () => return new PrismaClient();

	declare global {
		var prisma: undefined | ReturnType<typeof prismaClientSingleton>
	}
	
	const prisma = globalThis.prisma ?? prismaClientSingleton()
	
	export default prisma
	
	if(node.ENV !=== production) globalThis.prisma = prisma  //  globalThis won't change on hot reload.

MIDDLEWARES are generally used to run some operation before or after request is completed. For example for stuff like - Analytics, Authentication, logging, redirection, modifying request and response headers. 

- to create middlewares in nextjs , ONLY ONE FILE MIDDLEWARE.TS/MIDDLEWARE.JS IS TO BE IMPLEMENTED IN ROOT FOLDER.
We can break down functions in different files and then import them in middleware.ts for cleaner management. 

	import { NextRequest } from "next/server"
		let requestCounter = 0
	export function middleware(req: NextRequest) {
		requestCounter++ 
		return NextResponse.next();				// to call the next handler // instead of next() in expressjs, we do this. 
	}
